ฐานข้อมูลระบบตรวจงานแม่บ้าน

ตารางทั้งหมดที่ระบบใหม่ต้องใช้ ตาม ADR 0001–0056 · ทุกตารางบอกว่ามาจาก ADR ไหน · เขียนก่อนเริ่มแก้โค้ด เพื่อให้เห็นภาพรวมก่อนวางแผนพัฒนา

MySQL 8 Community15 ตารางEF Core + MySql.EntityFrameworkCoreตั้งชื่อ snake_caseเวลา UTC

ภาพรวม

สถานที่ (ตึก › Area › จุด › ป้าย › ช่วงรอบ) เป็นข้อมูลที่ Admin ตั้งค่า ส่วนการลงเวลา การส่งงาน การตรวจ และการสแกนที่ถูกบล็อก เกิดจากการสแกนที่หน้างาน ทุกการแก้ของ Admin ลง audit_log

สถานะการ์ดมาจากไหน

สถานะของจุดไม่ได้เก็บเป็นคอลัมน์ ระบบคำนวณสดทุกครั้งจากช่วงรอบปัจจุบัน งานที่ส่งในรอบนั้น และการตรวจของรอบนั้น สิ่งที่เก็บจริงคือผลการจัดงานเข้ารอบ (placement) ตอนแม่บ้านส่งงาน

  1. ต้องแก้ไขการตรวจล่าสุดของรอบเป็น FAIL และยังไม่มีงานส่งหลังจากนั้น
  2. เลยรอบรอบจบแล้ว ยังไม่มีงานส่ง
  3. รอตรวจมีงานส่งที่ยังไม่ถูกตรวจ
  4. ตรวจผ่านการตรวจล่าสุดเป็น PASS
  5. ยังไม่ทำรอบยังไม่จบ ยังไม่มีงานส่ง
  6. ยังไม่ถึงรอบกะเริ่มแล้ว รอบแรกยังไม่เริ่ม
  7. นอกเวลาArea ไม่มีกะนี้ หรือปิดใช้งาน

เรียงตามความสำคัญ ตัวบนชนะตัวล่าง · รอบใหม่เริ่มแล้วการ์ดเริ่มใหม่ ผลของรอบเก่า (ไม่ได้ทำ, ไม่ได้ตรวจ, ไม่ได้แก้) หาได้จากตารางเดียวกัน ไม่ต้องเก็บแยก · ป้าย "แจ้งปัญหา" มาจากงานล่าสุดที่ status = ISSUE

id คีย์หลักarea_id คีย์อ้างอิงNULL ว่างได้

กติกาที่ใครกัน

กติกาที่ฐานข้อมูลกันได้ ให้ฐานข้อมูลกัน เพื่อไม่ให้ข้อมูลผิดแม้แอปมีบั๊ก ส่วนกติกาที่ขึ้นกับเวลาและสถานะ แอปตรวจตอนสแกนหรือตอนบันทึก

กติกากันด้วยใครกัน
Area ละ 1 แม่บ้านต่อกะUNIQUE (cleaner_slot)ฐานข้อมูล
ตึกละ 1 หัวหน้าต่อกะUNIQUE (supervisor_slot)ฐานข้อมูล
1 ป้ายลงเวลาต่อ AreaUNIQUE (checkin_area_id)ฐานข้อมูล
ลงเวลาแต่ละแบบได้ครั้งเดียวต่อกะ (เวลาแรกชนะ)UNIQUE (user_id, shift_date, shift, event_type)ฐานข้อมูล
ไม่สะอาดต้องมีข้อบกพร่องCHECK บน inspectionsฐานข้อมูล

ช่วงรอบห้ามซ้อนกัน และต้องอยู่ในกะตรวจตอนบันทึกแอป

งานลบข้อมูล

ตาม ADR 0055 ช่วงทดลองแรกๆ ยังไม่ต้องรัน แต่ต้องเปิดใช้ก่อนข้อมูลจริงอายุถึง 90 วัน ตัวเลขทุกตัวอยู่ใน config

เมื่อไรทำอะไรหมายเหตุ
ทุกคืนลบ latitude, longitude, accuracy_m ของแถวที่อายุเกิน 90 วัน ใน shift_attendances, cleaning_submissions, inspections, blocked_scansdistance_m และ within_radius อยู่ต่อ
ทุกคืนลบ shift_attendances และ blocked_scans ที่อายุเกิน 1 ปี
ทุกต้นเดือนสรุปเดือนที่อายุครบ 1 ปีลง point_monthly_summaries แล้วลบ cleaning_submissions, inspections ของเดือนนั้นไม่มีชื่อคนในสรุป
ทุกคืนลบ audit_log และ alert_reviews ที่ชี้ไปยังแถวที่ถูกลบแล้วเก็บนานเท่ากับข้อมูลที่ถูกแก้
ทุกคืนลบ refresh_tokens ที่หมดอายุเกิน 30 วัน

จากตารางเดิม

โค้ดตอนนี้มี 4 ตารางจากเฟสแรก ยังไม่มีข้อมูลจริง จึงสร้าง migration ชุดใหม่ได้เลย

ตารางเดิมตารางใหม่เปลี่ยนอะไร
service_pointsservice_points + signsย้าย qr_token ไปที่ signs · เลิกใช้ location และ cleaning_interval_minutes (แทนด้วย point_round_windows)
scan_recordscleaning_submissionsเพิ่มรอบ, placement, ทำแทน, GPS
usersusersusername + password_hash → employee_id + secret_hash (Admin ยังใช้ username) · เพิ่ม area, building, shift
refresh_tokensrefresh_tokensใช้เหมือนเดิม
–buildings, areas, point_round_windows, cover_assignments, shift_attendances, inspections, blocked_scans, alert_reviews, audit_log, point_monthly_summariesตารางใหม่

สิ่งที่ตัดสินตอนออกแบบ

เรื่องเทคนิคที่ ADR ไม่ได้บอก ผมเลือกไว้แบบนี้ แก้ได้ก่อนเริ่มเขียนโค้ด

วันของกะดึกshift_date คือวันที่กะเริ่ม กะดึก 19:00 วันที่ 7 ถึง 07:00 วันที่ 8 นับเป็นวันที่ 7 ทั้งกะ
เวลาเก็บ DATETIME เป็น UTC ตามเวลาเซิร์ฟเวอร์ ส่วนช่วงรอบเก็บเป็น TIME เวลาไทย แอปแปลงให้
สำเนาเวลารอบcleaning_submissions เก็บ round_start, round_end ไว้ด้วย เพราะ Admin แก้หรือลบช่วงรอบทีหลังได้ แต่ประวัติต้องบอกได้ว่าตอนส่งเป็นรอบไหน
สถานะการ์ดไม่เก็บเป็นคอลัมน์ คำนวณสดจากช่วงรอบ งานส่ง และการตรวจของกะนี้ (ตามนิยาม Point Status)
GPSเก็บเป็นคอลัมน์ในแต่ละตาราง ไม่แยกตาราง เพราะงานลบพิกัดหลัง 90 วันแค่ตั้งค่า 3 ช่องเป็น NULL
บัญชีตารางเดียวทุกบทบาทอยู่ใน users ใช้คอลัมน์คำนวณกับ UNIQUE กันคนซ้ำในช่องเดียวกัน ปิดใช้งานแล้วช่องว่างเอง
ลงเวลาก่อนกะต้นแบบให้ลงเวลาได้ตั้งแต่ 1 ชั่วโมงก่อนกะเริ่ม (เช่น 06:52 นับเป็นกะเช้า) ตัวเลขอยู่ใน config ยังไม่มี ADR
migrationยังไม่มีข้อมูลจริง สร้าง migration ชุดใหม่ตั้งแต่ต้นได้ ไม่ต้องย้ายข้อมูล
