# Automatic data retention

Date: 2026-11-03. Authority: owner explicitly requested implementing retention now and selected both GPS 90 days and one-year deletion/monthly summaries. Implements facility-0055 and the cleanup design in docs/design/database.html; no PDPA notice work. Delivery stays local on codex/automatic-data-retention until publication is requested.

## Behavior

- Run once after normal application startup/migrations, then nightly at 02:00 Asia/Bangkok. Catch up after downtime. Single-server application; no external scheduler/package or HTTP maintenance endpoint. Cancellation stops cleanly; failures log only counts/context and retry after 15 minutes without terminating serving.
- GPS age uses each record's observed timestamp: ShiftAttendance.OccurredAt, ScanRecord.SubmittedAt, InspectionRecord.InspectedAt, BlockedScan.ScannedAt. At or before now UTC minus GpsDays (default 90), set Latitude, Longitude, AccuracyM to null. Preserve DistanceM/WithinRadius and all record fields. Never clear Sign setup coordinates. Repeated execution is harmless. Use bounded SQL batches, cancellation and no loading of full GPS data.
- Attendance and BlockedScan age out at or before now.AddYears(-RecordYears), default one year. Remove associated typed AlertReview and AuditEntry rows in the same transaction, avoiding same-ID collisions across tables.
- As in the original database design, submissions/inspections are archived in complete Thai shift-date calendar months: in November 2026 with a one-year setting, archive through October 2025; November 2025 waits until December 2026. This preserves the current month plus twelve completed months, rather than deleting half a reporting month. Explicitly document this month-boundary consequence. Never delete a source/inspection newer than the one-year timestamp cutoff even if its shift date is old; defer that month.
- Before deleting an eligible month, write one PointMonthlySummary per point/month. Primary key is ServicePointId + Month (first day). No user IDs, names, employee IDs, notes, defects, QR, GPS or cover references in summaries. Fields: RoundsTotal, SubmittedOnTime, SubmittedLate, NotDone, InspectedPass, InspectedFail, NotInspected, IssuesReported. Count each submitted round once by point/shift date/shift/copied start+end; rework/resubmission does not create another round. On-time versus late uses the first submission for the round; inspections pass/fail count actual verdict records, IssuesReported counts Issue submissions (including off-round). NotInspected counts finished submitted rounds whose final outcome is NotInspected; NotReworked is not silently counted as NotInspected.
- Expected missing rounds follow existing Excel semantics: current active point/Area/window definitions with CreatedAt <= round start, plus copied rounds from historic submissions even if a window was deleted. Document this inherited limit; do not invent historical schedule snapshots. Existing point-month summary is the completion marker; save summary and delete source/inspection/dependent history in one transaction. Re-run never recomputes a previously archived month from its now-deleted data or counts twice. Unique summary keys plus transactional writes guard concurrent attempts; the server design remains single-instance.
- Cover assignments older than the cutoff can be removed only when no retained scan/inspection references them; remove their audit rows with them. Delete expired refresh tokens only after an additional 30-day grace (the existing design), preserving tokens needed for reuse detection. Keep master entities (users, buildings, Areas, service points, signs) and setup/account audit history for retained entities.
- Settings in Retention section, validated at startup: Enabled (default true), GpsDays=90, RecordYears=1, RunAtHour=2, BatchSize=1000 (bounded 1..10000), RetryMinutes=15, RefreshTokenGraceDays=30. Positive safe ranges; invalid settings fail startup rather than using a zero cutoff. Testing environment disables automatic worker startup to preserve fixture initialization; worker tested directly. Development is enabled because it must exercise the same policy, but do not launch the owner's API/database during implementation.
