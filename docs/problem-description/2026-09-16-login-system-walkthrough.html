💡 ยินดีต้อนรับสู่ Interactive Walkthrough: ระบบ Login & Persistent Session
ระบบนี้ออกแบบตามสถาปัตยกรรมความปลอดภัยระดับสูง เพื่อตอบสนองการใช้งานจริงของพนักงานทำความสะอาดบนมือถือ (สแกน QR Code) ควบคู่กับหน้าจอ Dashboard ของผู้บริหาร โดยยึดหลักเกณฑ์สำคัญตาม ADR facility-0010 ถึง facility-0018
📄 โค้ดส่วน Frontend: LoginPage.tsx และ authSession.ts

// frontend/src/features/auth/components/LoginPage.tsx const handleSubmit = async (e) => { e.preventDefault(); const ok = await login(username, password); // เรียก useAuth() -> AuthContext if (ok && onSuccess) onSuccess(); }; // frontend/src/services/authSession.ts export async function login(username: string, password: string): Promise<AuthUser> { const res = await fetch('/api/auth/login', { method: 'POST', headers: { 'Content-Type': 'application/json' }, credentials: 'same-origin', // สำคัญมาก: เพื่อให้เบราว์เซอร์รับ Set-Cookie body: JSON.stringify({ username, password }), }); ... }

🔒 ทำไมถึงแยกเก็บ Access Token ใน Memory และ Refresh Token ใน HttpOnly Cookie?
ตามข้อตกลงสถาปัตยกรรม ADR facility-0013:
[Browser Client] ├── In-Memory (JavaScript variable): เก็บ Access Token (JWT อายุ 5 นาที) │ └── ถ้ามีช่องโหว่ XSS สคริปต์ที่แอบรันอาจขโมยได้แค่ Token อายุ 5 นาที └── HttpOnly Cookie (facility_refresh): เก็บ Refresh Token (อายุ 30 วัน) └── JavaScript ไม่สามารถอ่านค่าได้เด็ดขาด (document.cookie จะมองไม่เห็น) └── ตั้งค่า Path=/api/auth ทำให้ส่งไปเฉพาะ route auth เท่านั้น ไม่รั่วไป API อื่น
📄 โค้ดส่วน Frontend: การขอ Access Token ใหม่อัตโนมัติ (authSession.ts)
จัดการปัญหาการแข่งกัน Refresh พร้อมกัน (Concurrent Refresh) ด้วย inflightRefresh:
// frontend/src/services/authSession.ts let inflightRefresh: Promise<AuthResponse | null> | null = null; export function refreshSession(): Promise<AuthResponse | null> { // ADR facility-0015: มีได้แค่ 1 refresh request ในเวลาเดียวกัน if (!inflightRefresh) { inflightRefresh = runRefresh().finally(() => { inflightRefresh = null; }); } return inflightRefresh; }
📄 โค้ดส่วน Backend: Token Rotation & Sliding Window 30 วัน
เมื่อ Refresh สำเร็จ Token เดิมจะถูกบันทึก RotatedAt = now และออกใบใหม่ทันที:
// backend/src/FacilityRealtime.Api/Endpoints/AuthEndpoints.cs stored.RotatedAt ??= now; // บันทึกเวลาที่ถูกหมุน var next = AddRefreshToken(db, stored.UserId, stored.SessionId, now); await db.SaveChangesAsync(); WriteRefreshCookie(http, next.Token, next.ExpiresAt, jwt.Value); return Results.Ok(ToResponse(stored.User, issuer.Issue(stored.User)));
❓ คำถามสำคัญ (Key Question) สำหรับผู้อ่าน

สมมติเหตุการณ์: โทรศัพท์ของผู้ใช้เพิ่งนำ Token-A มารีเฟรชได้รับ Token-B ไปเรียบร้อย (Token-A จึงมีสถานะว่าถูกหมุนแล้ว)

แต่ 2 นาทีต่อมา มี Hacker ที่ดักจับ Token-A ไปได้จากเครือข่าย พยายามส่ง Token-A มาขอ Access Token บ้าง...

👉 เซิร์ฟเวอร์ควรตอบสนองอย่างไร? แค่ปฏิเสธคำขอของ Hacker (401) แล้วปล่อยให้ผู้ใช้จริงใช้งานต่อ? หรือมีมาตรการที่รัดกุมกว่านั้น?

🚨 ตรวจพบ Token Reuse: Revoke ทันทีทั้ง Session (ADR facility-0015 / RFC 9700)
เซิร์ฟเวอร์ไม่สามารถรู้ได้ว่าใครคือเจ้าของจริง และใครคือ Hacker จึงต้องปกป้องข้อมูลด้วยการ ยกเลิกทุก Token ใน Session นั้น:
// backend/src/FacilityRealtime.Application/Auth/RefreshTokenRules.cs public static RefreshDecision Decide(RefreshToken token, DateTime nowUtc) { if (token.RotatedAt is not null) { // ภายใน 30 วินาที: ถือเป็น concurrent refresh จากอีกแท็บ (อนุญาต) return nowUtc - token.RotatedAt.Value <= ReuseGrace ? RefreshDecision.RotateWithinGrace : RefreshDecision.ReuseDetected; // เกิน 30 วินาที: ตรวจพบการขโมย! } ... }
📄 โค้ดส่วน Logout: การเพิกถอน Session อย่างสมบูรณ์
เมื่อผู้ใช้กด "ออก" ในแอป:
// backend/src/FacilityRealtime.Api/Endpoints/AuthEndpoints.cs private static async Task<IResult> LogoutAsync(...) { // ดึง SessionId จาก Token ที่ส่งมา แล้วสั่ง RevokeSession ใน Database if (sessionId is not null) { await db.RevokeSessionAsync(sessionId.Value, clock.GetUtcNow().UtcDateTime); } // สั่งเบราว์เซอร์ให้ลบ Cookie ทิ้ง http.Response.Cookies.Delete(RefreshCookieName, RefreshCookieOptions(jwt.Value)); return Results.NoContent(); }
🎯 สรุปจุดเด่นด้านสถาปัตยกรรม & ข้อแลกเปลี่ยน (Trade-offs)

✅ ข้อดีด้านความปลอดภัย (Security Strengths)

  • No LocalStorage XSS: Access Token อยู่ใน Memory เท่านั้น เมื่อปิดแท็บจะหายไป
  • HttpOnly Cookie: Refresh Token ถูกซ่อนจาก JavaScript 100%
  • Sliding 30 Days: ผู้ใช้หน้างาน (พนักงานทำความสะอาด) ไม่ต้องล็อกอินใหม่ทุกวัน
  • Automatic Reuse Revocation: ตรวจจับการขโมย Token และตัดวงจรทันที

⚖️ ข้อแลกเปลี่ยนที่ต้องแลก (Architectural Trade-offs)

  • Stateful on Server: เซิร์ฟเวอร์ต้องเก็บตาราง refresh_tokens ไม่ใช่ Stateless JWT ล้วน
  • Reload Network Call: เมื่อผู้ใช้ Refresh หน้าจอ เบราว์เซอร์ต้องยิง /api/auth/refresh 1 ครั้งเสมอเพื่อขอ Access Token ใหม่
  • Same-Origin Dependency: Cookie ส่งได้เฉพาะโดเมนเดียวกัน (Path=/api/auth) หากแยก API ข้ามโดเมนต้องตั้งค่า CORS/Credentials อย่างรัดกุม
