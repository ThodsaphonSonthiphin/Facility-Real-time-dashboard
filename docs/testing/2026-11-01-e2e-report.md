## Project analysis that informed the tests

The frontend is React19, TypeScript, Vite, Tailwind and Redux Toolkit/RTK Query. Routing enforces Admin/Cleaner/Supervisor pages. The backend is .NET10 ASP.NET Core with real HTTP endpoints and SignalR notifications; EF Core persists to MySQL. Authentication uses the implemented role-specific login, access/refresh tokens and server authorization policies. Existing Development fixture identities are read from the source, rather than invented endpoints or credentials.

Buildings contain Areas; Areas contain service points and dated round windows. Cleaners have an optional Area and a shift; Supervisors have a Building and shift. Signs identify check-in locations and points. Attendance gates Cleaner submissions. A Supervisor inspects a submission as Passed/Rework; resubmission and live updates connect both roles. Covers, alerts, audit history, inspection summaries and Excel exports depend on those relationships. Domain rules and actual implementations were examined before generating these records.

Playwright was already declared; no second browser framework or fake-data dependency was introduced. Existing9 cases were retained and expanded to26, then27 with the approved navigation fix. The runner builds the frontend into a private published API directory and serves both from `http://127.0.0.1:5101` (configurable), without requiring or replacing the owner's Vite/review server. It waits for health and seeded database readiness before opening Chromium.

## What was implemented

- A Python standard-library lifecycle runner behind the existing npm/shell entry points, with private app directories, owned database/account creation, readiness checks and cleanup on success/failure.
- Default visible Chromium,350ms slow motion, one worker, no automatic mutation retries, bounded timeouts, screenshots, traces, HTML and JSON reports.
- A test-only EF console factory with baseline/small/medium/large profiles, fixed codes and distributions, real entity/round validation, ownership checks, repeat-seed checks and semantic integrity checks.
- Browser evidence for uncaught page errors and HTTP5xx, including both contexts in multi-role workflows; response durations, layout-shift sources and workbook validation in generated reports.
- Tests for authentication/access, Admin setup, validation/confirmation, attendance, covers, large lists, history cursors, summary accuracy, Excel and two live workflows.
- ADR facility-0102, updated E2E/handover documentation and8 automated lifecycle safety checks.

Each run creates a new database name without `IF NOT EXISTS`; it never adopts or resets an existing database. A private manifest and database token must match before cleanup. Only a successfully created database user may be removed. The API/factory get a restricted user for that database. Existing databases, shared `wwwroot` and unrelated processes are outside cleanup. User-owned backend project/IDE changes and Export comments remain outside this implementation.

## Untested or partially covered

Safari/Firefox, physical GPS accuracy, camera QR scanning, paper printing, network-loss recovery, concurrent-user capacity, token-reuse/throttling security, every credential-change variant, every cover/alert transition and all shift/round boundaries were not exhaustively tested. Supervisor live rework is covered; a complete alert-management workflow is not. Role checks are representative, not an endpoint-by-endpoint authorization audit. Workbook structure/rows are checked, not every exported cell against independent business totals.

The suite uses one shared fresh database per run and one worker; individual mutation cases are not all safe to retry in that same database. Re-run the runner for a fresh environment. Attendance paging skips on small data; the original live case skips19:00–20:00 Bangkok before its first Night round, and generated rework skips the last2minutes before a shift change. The main large run had no skips. No source assertion was relaxed to hide the discovered layout defect.
