# งานเก็บ ลบ และสรุปข้อมูลอัตโนมัติ

งานนี้ทำตาม facility-0055 และแบบงานลบใน `docs/design/database.html` เจ้าของเลือกให้ทำครบทั้ง GPS 90 วันและข้อมูลรายครั้ง 1 ปีเมื่อ 3 พ.ย. 2026 สถานะการทดสอบและการเผยแพร่ล่าสุดอยู่ใน [handoff](handoff.md)

## ลบอะไร และเก็บอะไรไว้

| ข้อมูล | เมื่อครบอายุ | สิ่งที่ยังอยู่ |
|---|---|---|
| GPS ของการลงเวลา ส่งงาน ตรวจงาน และการสแกนที่ถูกบล็อก | อายุ 90 วัน ล้าง latitude, longitude และ accuracy_m | ตัวรายการ ระยะห่างจากป้าย และผลใน/นอกรัศมี |
| การลงเวลาและการสแกนที่ถูกบล็อก | อายุ 1 ปี ลบตัวรายการพร้อมประวัติ Admin/การปิดเตือนที่ผูกกับรายการนั้น | บัญชีและข้อมูลตั้งค่าพื้นที่/ป้าย |
| การส่งงานและการตรวจงาน | สรุปเดือนที่ครบอายุก่อน แล้วลบรายการรายครั้งพร้อมประวัติที่ผูกอยู่ | สรุปรายเดือนต่อจุด ไม่มีชื่อหรือรหัสผู้ใช้ |
| การมอบหมายทำแทนเก่า | ครบ 1 ปี และไม่มีการส่งงาน/ตรวจงานที่ยังเก็บอยู่ใช้อ้างอิง | ข้อมูลตั้งค่าของบัญชี พื้นที่และตึก |
| Refresh token หมดอายุ | หลังหมดอายุเพิ่มอีก 30 วัน | Session ที่ยังไม่ถึงเกณฑ์ลบ |

พิกัดที่ Admin เก็บไว้เป็น **ตำแหน่งของป้าย** เป็นข้อมูลตั้งค่า จึงยังอยู่ ส่วนไฟล์ Excel ที่ดาวน์โหลดและ backup อยู่นอกงานนี้ การเก็บ journal 90 วันเป็นการตั้งค่าของ host ตาม [handover](handover.md) แยกจากการลบในฐานข้อมูล

### การนับอายุ

GPS ใช้เวลาของการลงเวลา/ส่งงาน/ตรวจงาน/สแกนที่ถูกบล็อกแต่ละรายการ เทียบกับเวลาปัจจุบัน UTC ล้างเมื่อเวลาเท่ากับหรือเก่ากว่าเส้นตัด 90 วัน จำนวนวันอยู่ใน config

การลงเวลาและสแกนที่ถูกบล็อกใช้เส้นตัด 1 ปีปฏิทิน (`AddYears(-1)`) ส่วนการส่งงานและการตรวจใช้ **เดือนเต็มของวันที่กะ เวลาไทย** ตามแบบเดิม เพื่อไม่ให้สรุปครึ่งเดือน เช่น:

| รันงานเมื่อ | เดือนที่สรุปและลบได้ |
|---|---|
| 3 พ.ย. 2026 | ต.ค. 2025 และก่อนหน้า |
| 1 ธ.ค. 2026 | พ.ย. 2025 และก่อนหน้า |

ดังนั้นข้อมูลส่งงาน/ตรวจงานอาจอยู่เกินวันครบรอบ 1 ปีจนถึงขอบเดือนถัดไป เก็บเดือนปัจจุบันและ 12 เดือนที่จบแล้ว หากรายการหรือการตรวจในเดือนเก่ามีเวลาจริงที่ยังอายุไม่ครบ 1 ปี ให้รอเดือนนั้นก่อนเพื่อไม่ลบข้อมูลใหม่ตามวันกะเก่า

## สรุปรายเดือน

ตาราง `point_monthly_summaries` ใช้จุดและวันแรกของเดือนเป็น key ไม่มีผู้ใช้ ชื่อ รหัสพนักงาน หมายเหตุ ข้อบกพร่อง token พิกัด หรือข้อมูลการมอบหมายทำแทน

เก็บจำนวนรอบทั้งหมด รอบส่งตรงเวลา รอบส่งช้า รอบไม่ได้ทำ ผลตรวจผ่าน ผลให้แก้ รอบไม่ได้ตรวจ และรายการแจ้งปัญหา การส่งแก้งาน/ส่งซ้ำในรอบเดียวไม่เพิ่มจำนวนรอบ ส่วนผลตรวจนับตามจำนวนครั้งที่ตรวจ และการแจ้งปัญหานับรายการ Issue รวมส่งเพิ่มนอกเวลา

การนับรอบที่ไม่ได้ทำใช้กติกาเดียวกับ Excel ปัจจุบัน: การตั้งค่าจุด/พื้นที่/รอบที่ใช้งานอยู่ โดยดูว่า window ถูกสร้างทันก่อนรอบนั้นเริ่มหรือไม่ ประวัติรอบที่เคยมีการส่งใช้เวลารอบที่คัดลอกไว้ในรายการ แม้ window จะถูกลบภายหลัง **ระบบไม่มี snapshot ประวัติตารางรอบทั้งหมด** จึงไม่แต่งจำนวนรอบที่ไม่เคยส่งจากตารางเก่าที่ไม่มีหลักฐานแล้ว

การบันทึกสรุปและลบข้อมูลต้นทางอยู่ใน transaction เดียวกัน ถ้าล้มเหลวต้องไม่มีทั้งสรุปค้างและข้อมูลหาย การรันซ้ำอ่าน marker ของเดือนที่สรุปแล้ว จึงไม่คำนวณซ้ำจากข้อมูลที่ลบไปแล้วและไม่เพิ่มยอดซ้ำ ทุกรอบตามเก็บรายการปิดเตือน/ประวัติของข้อมูลรายครั้งที่ไม่มีต้นทางแล้วด้วย เผื่อมีการกดปิดเตือนพร้อมกับที่งานลบต้นทาง การตรวจใช้ชนิดข้อมูลและเลข ID คู่กัน จึงแยกเลข ID เดียวกันของคนละตารางได้

## การรันและตั้งค่า

API ทำงานครั้งแรกหลัง startup/migration แล้วรันทุกคืน **02:00 เวลาไทย** ถ้าเครื่องปิดอยู่จะเก็บตกตอนเริ่มระบบใหม่ ใช้ได้ทั้ง Linux และ Windows ไม่ต้องติดตั้ง cron หรือบริการภายนอกเพิ่ม เมื่อรันล้มเหลวเขียน Server Log แล้วลองใหม่หลัง 15 นาที การให้บริการ API ยังทำต่อได้

ค่าตั้งอยู่ในส่วน `Retention` ของ appsettings หรือ environment variable ในไฟล์ค่าของ host (เช่น `Retention__GpsDays`) ค่าตั้งที่ใช้ในงานนี้:

| ค่า | ค่าเริ่มต้น | ความหมาย |
|---|---:|---|
| `Enabled` | `true` | เปิดงานอัตโนมัติ |
| `GpsDays` | 90 | อายุพิกัดดิบเป็นวัน |
| `RecordYears` | 1 | อายุข้อมูลรายครั้งเป็นปีปฏิทิน |
| `RunAtHour` | 2 | ชั่วโมงที่รันประจำวัน เวลาไทย |
| `BatchSize` | 1000 | จำนวนแถวต่อ batch (1–10000) |
| `RetryMinutes` | 15 | รอกี่นาทีก่อนลองใหม่เมื่อเกิดข้อผิดพลาด |
| `RefreshTokenGraceDays` | 30 | ระยะเพิ่มหลัง token หมดอายุ |

ระบบต้องปฏิเสธค่าที่ไม่ผ่าน validation ตั้งแต่ startup ส่วน Testing ไม่เปิด worker อัตโนมัติ เพื่อไม่รบกวนการเตรียม fixture และใช้ direct tests ตรวจตัว worker แทน Development ใช้นโยบายเดียวกับระบบจริง จึงควรตรวจฐานข้อมูลที่เลือกก่อนเริ่ม API

Server Log เก็บจำนวน GPS ที่ล้าง สรุปที่สร้าง และรายการหลัก/cover/token ที่ลบ (ไม่นับแถวประวัติที่ลบตามไปด้วย) พร้อมชนิดข้อผิดพลาด ไม่บันทึกพิกัด ชื่อ ข้อความในฟอร์มหรือเนื้อหา record ไม่มี maintenance endpoint บนเว็บ การแก้ค่าในไฟล์ของ host ต้อง restart ระบบ

ก่อน deploy ให้สำรองฐานข้อมูลตามคู่มือ ตรวจ migration และตรวจผลรอบแรกใน journal ดู log ตาม [handover §2.5](handover.md#25-ให้ระบบรันเองตลอด-systemd) การตั้งเวลา/transaction ผ่านการทดสอบจำลองได้ แต่การรันตามเวลาจริงบน host ต้องยืนยันตอน deploy
